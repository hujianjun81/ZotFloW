# 方法关系图、实验图表与配图体检

### 什么时候该画

方法关系图优先采用能清楚解释核心机制的原图；需要整合分散关系或用户明确要求时可补绘。实验数据表转绘按 [实验图表准则](experiment-visualization.md)，不受方法原图优先规则限制。数据图采用可复现的 Python/Matplotlib 等工具；复杂多面板、排版或投稿级需求可结合已可用的 `nature-figure` skill，按其实际流程执行。精确损失关系与流程优先使用可编辑 `.drawio.svg`。按任务需要选用已有工具或 skill，不默认要求安装其他插件。方法补绘的典型场景：

- 论文把某条链路拆在正文里讲（如「预训练 → 零样本推理」全链路分散在多个章节，没有单张图覆盖）
- 跨章节/跨论文的对比关系，论文本身不可能有
- 用户明确要求整理成图

已有方法原图清楚时直接采用；补绘能更清楚说明关系时，明确标注原文依据与解释范围。同一关系不必同时嵌入表达重复的原图和补绘图，保留可回查的原图编号即可。

### 硬性约定

1. **重绘图必须显式标注来源**，紧跟在图下一行：
   ```
   > 📐 上图为**依据 §X.Y / Fig. N 整理绘制**（非论文原图）。
   ```
   **绝不可以把重绘图标作论文原图。** 用户判断"这是作者原话还是你的理解"全靠这个标注。
2. **不得因为"图难找"就退化成重绘。** 先按下面「配图体检」确认源里是否真有 —— 很多"图缺失"是假警报。
3. 图注与正文结论必须能在 `full.md` 里找到对应句子，不得凭空补充论文没有的判断。

### 文件格式（两段式，缺一不可）

`.drawio.svg` 必须**同时**含两部分，否则要么不能显示、要么不能编辑：

| 部分 | 作用 | 判据 |
|------|------|------|
| `<svg>…</svg>` 主体 | Obsidian 直接渲染 | 肉眼看到的就是它 |
| 根 `<svg>` 上的 `content` 属性 | 存放 URL 转义的 `mxGraphModel` | 插件的 `isDrawioData()` 解析它，通过才有铅笔图标可编辑 |

`content` 属性转义：`html.escape(model, quote=True)`（即 `<`→`&lt;`、`"`→`&quot;`、`&`→`&amp;`）。

**用 Python 生成，不要手写。** 要点：
- 顶点和连线放**同一张 shape 表**，SVG 体和 mxGraphModel 都由它渲染 —— 否则两边坐标会漂移
- 坐标用绝对像素；顶点数 = `<rect>` 数
- 生成后**必须校验**（下面的检查清单），不能生成完就交

**校验清单**（生成后立即跑）：

```python
ET.fromstring(raw)                      # 1. 整文件是良构 XML
ET.fromstring(html.unescape(content))   # 2. content 能反解
# 3. 反解根标签 in {mxfile, mxgraph, mxgraphmodel}   ← isDrawioData 白名单
# 4. 顶点 x+w <= viewBox 宽, y+h <= viewBox 高       ← 防溢出（最容易犯）
# 5. len(re.findall(r'<rect ', raw)) == 顶点数        ← 防两部分漂移
```

实测踩过的坑：方框索引从 1 开始写 `X0 + i*(BW+GAP)`，6 个框直接推出画布（视图宽 1120 / 模型到 1257）。**溢出不会报错，只会让图在 Obsidian 里被裁掉**，所以必须算。

### 嵌入笔记

```markdown
![[<名字>.drawio.svg]]
```

用 `![[…]]` 即可，与项目既有笔记写法一致。插件**没有注册 markdown 后处理器**（源码中 `registerMarkdownPostProcessor` 零次出现），嵌入走 Obsidian **原生** SVG 渲染，所以能正常显示；它只 `registerExtensionsReplace(["svg"], …)`，影响的是"点击文件时用哪个视图打开" —— 点进去才进 drawio 编辑器。

自绘方法图保留 `.drawio.svg`，自绘数据图保留 `.svg`；临时预览放 `.build/`，不交付同图的多个格式副本，不在最终回复单独列出配图。

在阅读视图点击图片可进入 drawio 编辑；无法进入时检查插件是否安装/启用，以及 `.obsidian/plugins/drawio-obsidian/data.json` 的初始化状态（`welcomeComplete: true`）。只检查用户实际使用的插件，不把缺配置自动解释为初始化崩溃。

### 配图体检

用户问"有没有笔记丢图"时跑：

```bash
python scripts/audit_figures.py --vault "<库根>" --selftest
```

`--selftest` 先植入两个必死引用验证检测器有效，再体检 —— **不加这个，"0 死链"是不可信的**
（检测器可能本身就是坏的，那它当然什么都发现不了）。

脚本输出两部分：

1. **阶段一 · 死链检测** —— 遍历所有 `.md`，抽出 `![[…]]` 与 `<img src="…">`，
   逐个在库根 / 笔记同级 / `figures/` 下解析。**只有这一部分是"真损坏"的判据。**
2. **阶段二 · 与 MinerU 比对** —— 按笔记里的 `Zotero Key` 找到解析目录，
   列出 `figureBlocks`（过滤无 `labelHints`/`captionHints` 的 logo 块），
   标出哪些是**字节级同源**、哪些**需人工确认**。

**判读时注意两个假阳性来源**，不要把数字直接当"漏拷"：

- **重新编码**：同一张图被重编码或从剪贴板粘贴过，**sha256 变但像素尺寸不变**。所以"文件名/哈希对不上"≠"图缺失"。要按尺寸或肉眼比对确认。
- **编辑取舍**：综述笔记本来就不会嵌入全部几十张图。"未引用 N 张"多半是选择，不是损坏。

**真正的损坏只有一种**：**死链** —— 笔记想显示但文件不存在。这才需要修。

修复方式：`read_mineru.py --key <KEY> --copy-figures --out <项目>/figures` 取回原图，替换引用，删掉 `⚠️ 该图缺失` 之类的注解。

> 踩过的坑：曾有笔记写「该图缺失（Zotero 源中无此文件，非迁移问题）」—— **归因是错的**，图就在 `llm-for-zotero-mineru/<dir>/images/` 里，只是当年没拷进来。**在断言"源里没有"之前，务必先去 MinerU 目录 ls 一遍。**
